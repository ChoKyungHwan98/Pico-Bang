## 설계 원칙: 복잡도를 개체가 아니라 무리에 둔다

이 게임의 AI에서 어려운 부분은 **한 마리가 얼마나 똑똑한가**가 아니다.
개별 몬스터의 행동은 순찰 → 수색 → 추격 → 복귀로 끝난다. 상태 5~6개면 충분하고,
여기에 HFSM·Utility·GOAP를 얹으면 얻는 것 없이 설명만 어려워진다.

어려운 것은 **다섯 마리가 무리로서 어떻게 움직이는가**다.
누가 누구를 부르고, 누가 어느 자리를 맡고, 대형을 언제 조이고 언제 포기하는가.

그래서 계층을 이렇게 나눴다.

| 계층 | 클래스 | 책임 |
|---|---|---|
| 감각 | `NoiseSystem` | 소리 사건을 전파. 누가 듣는지는 모른다 |
| 조정자 | `MonsterDirector` | **플레이어를 직접 보지 않는다.** 몬스터의 목격 보고만으로 차단·수색 지점을 나눠 준다 |
| 개체 | `MonsterAI` | 플랫 FSM 6상태. 5마리 모두 같은 FSM. 자기 감각으로 발견하고 명령(수색·차단·해제)을 수행한다 |

`MonsterDirector`는 씬에 배치할 필요가 없다 — 첫 호출 시 자동 생성된다.
**호출 규격은 무리를 부른 전역 몬스터의 인스펙터 값을 따른다.**

## 1. 소음 전파 (`NoiseSystem`)

### 구조
소리를 낸 쪽은 누가 듣는지 모르고, 듣는 쪽은 누가 냈는지 모른다.
`NoiseSystem.Emit(위치, 반경, 종류)` 한 줄이 전부다.

### 소리의 종류 — 두 가지로 나눈 이유

| 종류 | 발생 위치 | 기본 반경 | 의미 |
|---|---|---|---|
| `Shot` (발사음) | **플레이어** | 30m | 쏘는 순간 자기 위치가 드러난다 |
| `TargetDestroyed` (파괴음) | **과녁** | 45m | 더 크게 울리지만, 내 위치가 아니다 |

**설계 의도**: 기획의 "과녁을 부수면 들킨다"를 그대로 옮기면 순수한 벌점이 된다.
진행하려면 반드시 쏴야 하므로, 플레이어에게 선택지가 없는 세금이 되어버린다.

발생 지점을 분리하면 여기에 **수**가 생긴다.
멀리 있는 과녁을 쏘면 큰 소리가 *거기서* 나므로 몬스터를 유인할 수 있다.
가까운 과녁을 쏘면 발사음과 파괴음이 겹쳐 위험이 배가된다.
**"무엇을 쏘는가"가 곧 전술이 된다.**

> ⚠ **기획 확인 필요**: 이 분리는 기획서에 명시되지 않은 판단이다.
> 단일 소리(플레이어 위치에서만 발생)로 되돌리려면 `Target.destroyNoiseRadius`를 0으로 두면 된다.

### 청각 반경 — 역할별 비대칭

```
전역 몬스터 : hearingRange                     (기본 50m)
구역 몬스터 : hearingRange × zoneHearingScale  (기본 50 × 0.45 = 22.5m)
```

기획의 "4마리는 전역 몬스터보다 좁게 듣는다"를 비율로 구현했다.
개체마다 값을 따로 넣지 않고 비율로 둔 이유는 **한 곳만 만지면 전체 균형이 함께 움직이도록** 하기 위함이다.

### 소리는 정확한 위치를 주지 않는다 ★

```
어긋나는 거리 = (소리까지의 거리 / 가청 반경) × 가청 반경 × noiseAccuracyFalloff
```

가청 범위 끝자락에서 들린 소리일수록 엉뚱한 지점으로 향한다.

**설계 의도**: 소리가 정확한 좌표를 준다면 한 발만 쏴도 전원이 플레이어에게 직행한다.
그러면 플레이어에게 대응할 여지가 없고, 사격이 그냥 자살 버튼이 된다.
부정확하게 만들어야 **"들켰지만 아직 기회가 있다"**는 구간이 생긴다.
긴장은 이 구간에서 나온다.

`noiseAccuracyFalloff = 0`으로 두면 항상 정확해진다 — 난이도 조절 축으로 쓸 수 있다.

## 2. 조정자 (`MonsterDirector`) — "안전한 길을 줄이는 AI"

> 2026-09-12 기획 확정. 목표는 **"플레이어를 최단거리로 잡는 AI"가 아니라 "플레이어가 갈 수 있는 안전한 길을 점점 줄이는 AI"**.
> 조정자는 몬스터 한 마리가 아니다. 전역 몬스터도 맵을 뛰어다니는 몬스터이고, 조정자는 뒤에서 한곳에 몰리지 않게 조정하는 보이지 않는 시스템이다.

### 현재 동작 ★ — 2026-09-14 재설계 (아래 이전 절들보다 우선)

**왜 바꿨나 (테스트)**: 화면 값 기준으로 차단이 계속 `0/2`(늦음·관통 제외)였다 — 줄줄이를 막으려고 넣은 **제외 조건이 협동 자체를 없앴다.** 또 시야가 0.5초만 끊겨도 감독이 쫓던 몬스터에게 수색 명령을 내려, 모퉁이만 돌면 추격이 끝났다. 소리는 구역 몬스터 22.5m·발사음 30m로 거의 닿지 않았다.

**구조: 두 개의 뇌, 한 방향 정보**
```
감독(진짜 위치·속도를 앎) ──흐린 목적지만──▶ 몬스터(자기 눈에 보일 때만 정확한 위치)
```
- `MonsterDirector.TrackPlayer()`가 매 프레임 진짜 위치·속도를 읽는다. 이 값은 목적지를 만드는 데만 쓰고, 몬스터에게는 흐려서(`hintBlurRadius` 4m, 추적 힌트 3m) 준다.
- 흐림 방향은 개체마다 4초간 고정 — 매번 바꾸면 목적지가 튀어 몬스터가 흔들린다.

**사냥 팀 = 발견자 포함 3마리**
- 누가 보든 `StartHunt`: 발견자 + 실제 경로가 가장 짧은 2마리. 나머지는 순찰.
- 팀 밖 몬스터가 새로 발견하면 합류하고, 쫓고 있지 않은 팀원 중 가장 먼 개체가 비킨다.
- 2초마다 `ReviewTeam`: 팀 밖 몬스터가 가장 먼 차단 팀원보다 경로상 0.6배 이하로 가까우면 교대(도망친 쪽 구역 몬스터가 앞길로 올라옴).
- 포기한 팀원은 빠지고 빈자리는 가장 가까운 몬스터로 채운다. 빠진 개체는 5초간 다시 부르지 않는다.
- 종료: 팀에 추격자가 없고 마지막 목격 후 8초.

**차단 배치 (1초마다) — 제외 대신 비용**
- 후보: 플레이어 진짜 위치에서 8방향으로 바닥을 따라 뻗어 막히는 곳(최대 18m, 6m 미만 버림, 8m 안 병합).
- 비용 = 경로 길이×0.3 − 각도 점수×20(+ 추격자 방향과 멀수록, 플레이어가 향하는 쪽일수록) + 관통 30 + 다른 팀원 길 겹침 비율×25 − 가던 지점 유지 8.
- 싼 짝부터 확정, 확정한 방향은 막힘·길은 사용 중으로 반영. 후보가 모자란 팀원은 **자기 쪽 경로로 플레이어 20m 앞까지 접근**(뒤를 따라가지 않고 자기 방향에서 조임).
- "늦음·겹침이면 아예 안 보냄"은 폐기 — 억지로라도 **자기 쪽 길로** 보낸다.

**추적 — 끈질김**
- 추격자가 시야를 놓치면 수색으로 바뀌지 않고 1초마다 감독의 흐린 힌트로 목적지를 갱신하며 계속 쫓는다(상태 표시 "추적 N초").
- 끈질김: 처음 6초 → 놓칠 때마다 다음 값 ×0.7(최소 2초). 다시 보면 남은 시간은 채워지지만 줄어든 값은 사냥이 끝날 때까지 유지 → 모퉁이를 여러 번 돌면 결국 떨어져 나간다.
- 0.5초 안에 다시 본 한순간의 깜빡임은 "놓침"으로 치지 않는다(끈질김을 깎지 않음). 재현 테스트에서 시야가 깜빡이며 끈질김이 순식간에 줄어드는 게 보여 추가.
- 다 떨어지면 그 자리에서 2초 두리번("놓침") → 구역 밖이면 복귀.

**재현 테스트 (2026-09-14, AI 테스트 씬 자동 조작 22초)**: 맵 가운데서 전역 몬스터가 발견 → 플레이어가 남쪽으로 11m/s 도주.
- 1초: 팀 전역·A·C 결성, A·C 차단 이동. 2~7초: 전역이 모퉁이에서 "추적"으로 계속 쫓음(힌트 따라감), 8초에 끈질김 소진 → 포기.
- 6초: 남쪽 D가 가장 먼 A와 **교대**해 앞길로 올라옴 → 9초에 플레이어와 만나 추격(스크린샷 2번의 빨간 선 장면).
- 8초: 전역이 빠진 자리에 B 합류. 끝까지 동시 추격 최대 2.
- 한계: 플레이어가 멈춘 뒤 추격자 2마리가 같은 자리에 겹침(무적 상태라 계속 붙어 있음). 창이 뒤로 가면 게임이 멈춰 30초를 다 채우지 못함.

### 2026-09-17~18 수정 ★ (추격 1 · 우회 2)

**전제**: 플레이어는 과녁을 부수려고 거의 쉬지 않고 쏜다.

1. **못 본 채 추적할 때 속도 상한**(기획 A안): 추격 중이라도 시야를 놓친 동안에는 `huntNearSpeed`(10)를 넘지 않는다. 보고 있을 때와 막으러 갈 때는 거리 속도(10~14) 그대로. → 끝까지 달리면 떨칠 수 있게.
2. **멈칫 1회 한정 + 쿨타임 8초**: 멈칫은 순찰·복귀 중 처음 알아챌 때만. 이미 확인하러 가는 중이거나 쿨타임이면 멈추지 않고 목적지만 바꾼다(`noiseReactCooldown`).
3. **빙 돌아가기**: 막을 자리로 가는 최단 경로가 플레이어 6m 안을 지나면, 플레이어에게서 22m 떨어진 경유 지점을 들러 도는 길을 찾는다(`PlanApproach`). 돌아가도 8초를 넘으면 그 조합은 쓰지 않는다(`detourTimeLimit`). 몬스터는 경유 지점 → 막을 자리 순으로 간다(`CommandAmbush(point, waypoint, true)`, 상태 표시 "돌아가는 중").
4. **들어오는 쪽 가르기**: 차단 몬스터는 추격자가 오는 쪽과 `sideAngleMin`(90°) 이상, 차단끼리도 그만큼 다른 쪽. 만족하는 조합이 없으면 3 → 2(서로 60°) → 1(추격자와 60°) → 0(제한 없음) 단계로 완화하고, 요약에 "방향 겹침 허용"으로 남긴다.
5. **후보를 16방향으로**(기존 8), 병합 거리 8 → 6m. 진단에서 후보가 3~6곳뿐이라 방향 조건이 거의 항상 완화됐기 때문. 두 씬의 직렬화 값도 6으로 수정.
6. **AI 테스트 씬**: 좌클릭에 1.5초 간격(실제 사격 간격과 동일), 경유 지점을 하늘색 원·선으로 표시.

### (이전) 원칙 — 모르는 것은 모른다 (2026-09-12, 위 재설계로 대체)

**조정자는 플레이어를 직접 보지 않는다.** 아는 것은 몬스터가 보고한 목격 기록뿐이다.

| 마지막 이동 방향 | 목격이 이어지는 동안만 (연속 목격 위치 차이). 끊기면 **동결** |
| 발견자 (전역/구역) | 매 보고 |

- 놓친 순간부터 진짜 현재 위치는 모른다. 플레이어가 반대로 도망치면 AI는 원래 방향을 뒤진다 — **의도된 "따돌림"**.

### 차단 — "아직 막히지 않은 길에 서 있기" ★ (2026-09-13 개정)

**개정 이유 (테스트)**: 본 게임에서 몬스터 3마리가 복도 정면에서 한 줄로 뭉쳐 왔다. 추격 인원 제한은 동작했는데(`[차단 전환]` 로그) 차단으로 빠진 몬스터도 결국 같은 곳으로 왔다. 원인:
1. 차단 지점이 "이동 방향 앞"뿐 — 플레이어가 몬스터 쪽으로 달리면 "앞" = 추격자가 오는 방향.
2. 복도에서는 앞·앞-좌·앞-우를 벽까지 당기면 전부 같은 복도 위의 점이 됐다.
3. 새로 발견한 몬스터가 먼저 추격에 들어간 뒤 빠져서(2초 역할 잠금) 그동안 3마리가 같이 쫓았다.
4. 차단 대기 몬스터가 8m 안에서 보면 무조건 덮쳐, 곧바로 다시 3마리가 됐다.
5. 배정 비용이 직선거리라, 벽 너머 가까운 지점을 고르면 실제 경로는 플레이어 뒤를 따라 도는 같은 길이었다.

**지금 방식**
- **8방향 후보**: 마지막 목격 위치에서 8방향으로 바닥을 따라 최대 18m 뻗어 막히는 곳이 후보. 6m도 못 가고 막히면 버리고, 8m 안에 겹치면 합친다 → 복도에서는 양 끝 두 방향만 남는다.
- **점수**: 이미 누가 오고 있는 방향(추격자 위치·다른 차단 지점)과 각도가 멀수록 +, 마지막 이동 방향 쪽이면 보조 +(0.35), 추격자 10m 안이면 −1. 고른 방향은 "막힘"으로 쳐서 다음 선택에 반영.
  → 복도에서 정면으로 달리면 추격자 방향은 막혀 있으니 **복도 반대쪽 끝(플레이어 뒤)**이 뽑힌다 = 앞뒤 협공.
- **배정은 실제 경로 길이**(`NavMesh.CalculatePath`) + 경로의 각 구간이 목격 위치 6m 안을 지나면 가산점.
- **추격 허가제**: 플레이어를 보면 추격에 들어가기 전에 조정자에게 묻는다. 가득 차 있으면 거부 + 즉시 빈 길로 차단 → 한 순간도 초과되지 않는다. 전역 몬스터는 항상 허가(가장 먼 구역 추격자가 비켜준다).
- **덮치기도 허가제**: 차단 대기 중 8m 안에서 봐도, 가장 먼 구역 추격자보다 3m 이상 가까울 때만 교대. 아니면 자리를 지킨다.
- AI 테스트 씬에 후보 8방향 선(선택 보라·미선택 회색·버려짐 흐린 회색)과 점수를 표시한다.

### 줄줄이 방지 ★ (2026-09-14 개정)

**개정 이유 (AI 테스트 씬)**: 전역·B 두 마리가 차단으로 가면서 같은 복도에 7.5m 간격으로 붙어 한 줄로 갔다. 정지 화면에서 값을 읽어 확인한 원인:
1. **차단 지점이 플레이어에게 너무 가까웠다.** 좁은 방에서 8방향 후보가 6.6m·8.0m 지점 — 플레이어는 0.6초면 닿는데 몬스터는 4.5~7초. 차단이 아니라 사실상 "플레이어에게 달려가기".
2. **두 몬스터의 경로가 63% 겹쳤다**(같은 복도). 지점은 달라도 가는 길이 같으면 줄이 된다.
3. B의 경로는 플레이어 방 한가운데를 지나갔다 — 관통을 **가산점**으로만 처리해서 걸러지지 않았다.
4. 보지 못한 몬스터도 추격 속도로 달려 앞 몬스터에 따라붙었다.
5. 직접 추격 중인 D에 옛 [수색] 명령 표시가 남아 있었다.

**지금 방식**
- 후보는 그대로 8방향. 대신 **몬스터 × 후보 짝마다 실제 경로를 계산해 걸러낸다.**
  - **관통**: 경로가 목격 위치 6m 안을 지나면 제외(가산점 → 제외로 강화).
  - **늦음**: 몬스터 도착(경로 ÷ 추적 속도)이 플레이어 예상 도착(목격 위치→후보 거리 ÷ 가정 속도 11 − 정보 나이)보다 3초 넘게 늦으면 제외. 늦게 가면 결국 뒤를 따라간다.
  - **겹침**: 사냥 중인 다른 몬스터가 **지나온 길(최근 6초) + 가려는 길**과 50% 넘게 겹치면 제외 = 줄 서기 금지.
  - 남은 짝 중 (늦는 시간 + 이동 시간 × 0.15 − 각도 점수 × 2)이 가장 싼 것부터 확정.
  - **알맞은 짝이 없으면 차단 수를 채우지 않는다.** 억지로 보내면 줄이 된다. 차단 수 = max(목표 수, 추격에서 빠진 수)로 정리(예전엔 더했다).
- **줄줄이 감지(안전장치)**: 같은 방향(속도 방향 차이 약 37° 이내)으로 움직이는 몬스터 바로 뒤 7m·옆 3m 안에 1초 이상 붙어 가면 —
  추격자끼리면 뒤쪽 구역 몬스터를 다른 빈 길로 / 차단 이동 중이면 앞 몬스터 길을 뺀 빈 길로. 빈 길이 없으면 그대로 둔다. 순찰·수색·복귀 몬스터는 건드리지 않고(멈추면 존재감이 사라짐), 사냥 중일 때만 검사한다. 한 번 끊은 개체는 3초간 다시 건드리지 않는다.
  (처음엔 수색·순찰 개체를 1.5초 멈추는 "양보"와 최근 6초 지나온 길 비교가 있었으나 이후 작업에서 제거 — 지금은 현재 위치 + 가려는 길만 비교)
- **추적 속도**: 플레이어를 보지 못한 채 움직일 때(추격 중 놓침·수색 이동·차단 이동)는 추격 속도 × `trackSpeedRatio`. **현재 기본값 1.0**(처음 0.75 → 포위가 늦어진다는 이유로 1.0으로 되돌림, 기획 확인 필요).
- **차단 도착 시간**: 플레이어 예상 도착도 직선거리가 아니라 목격 위치→후보의 실제 경로 길이로 계산.
- **유효한 빈 길이 없으면 차단을 보류**한다(제자리 대기 명령을 주지 않음). 교대할 추격자를 빈 길로 못 보내면 새 추격도 허가하지 않는다 — 최대 추격 수 초과 방지.

### 과녁 경보 (2026-09-14 추가)
- 발사 순간의 플레이어 위치·시각을 저장해 두었다가, 과녁이 **처음** 부서질 때 조정자에 전달(`Target.OnHit(발사 위치, 발사 시각)` → `ReportTargetAlarm`).
- 목격이 아니므로 이동 방향은 없음. 보지 못한 몬스터를 추격으로 바꾸지 않는다. 더 최근 목격이 있으면 덮어쓰지 않는다.
- 경보 위치까지 실제 경로가 가장 짧은 가용 몬스터 1마리가 조사, 이어서 작은 차단 배치.

### 첫 순찰 버그 수정 (2026-09-14)
- 상태 기본값이 이미 `Patrol`이라 시작 시 `ChangeState(Patrol)`이 무시되어 **첫 목적지가 잡히지 않았다.** 시작·재시작 때 목적지를 직접 고르도록 수정.
- 전역 몬스터가 `useGlobalNavMesh = 0`이라 구역 반경 안에서만 순찰하던 씬 설정을 두 씬 모두 1로 수정.
- 수색 분산 배정도 먼저 정한 몬스터의 길과 겹치면 비싸게 친다. 경로 없는 수색 지점에는 보내지 않는다.
- 직접 추격을 시작하면 남아 있던 수색·차단 명령 표시를 지운다.
- AI 테스트 씬: 후보 점수 옆에 제외 이유(늦음/관통/겹침), 패널에 "줄줄이 끊음 N회"와 이번 차단 계산 요약.
- **길목 지정은 하지 않기로 했다**(기획 결정) — 맵에 사람이 길목을 찍는 방식은 과하다고 판단.

(이전 방식 — 아래는 개정 전 기록)
- 차단 지점은 전부 **마지막 목격 위치 + 마지막 이동 방향**으로만 계산한다. 멈춰 있었으면 추격자 반대편을 방향으로 쓴다.
- 벽 너머로 잡히지 않게 걸을 수 있는 바닥 위에서 막히는 곳 바로 앞까지만 간다 (복도가 꺾이면 모퉁이 앞).
- 배정: 몬스터 × 지점 비용 = 거리 + **목격 위치 근처를 관통하는 경로 가산점** — 뒤에 있던 몬스터가 플레이어를 뚫고 앞으로 가는 것 방지. 이미 차단 중이던 개체는 소폭 우대(자리 교체로 우왕좌왕 방지).
- 차단 개체는 도착하면 대기. 멀리서 플레이어를 봐도 자리를 지키며 보고만 하고, 8m 안이면 덮친다.
- 덮쳐서 추격자가 3마리가 되면 가장 뒤처진 구역 몬스터가 대신 차단으로 빠진다(전역 몬스터는 추격 유지) — 뒤따르던 놈과 앞에서 기다리던 놈이 교대.

### 수색 분산 — 한 점에 뭉치지 않기

놓치면 사냥 참여자(추격하다 놓친 개체 + 차단·수색 명령을 받은 개체)에게 서로 다른 지점을 준다.
1번 = 마지막 목격 위치(가장 가까운 개체), 나머지 = 방향 쪽 부채꼴(앞 8m, 앞-좌/우 10m, 앞 18m, 좌/우 8m). 방향을 모르면 둘레에 고르게.
다시 보이기 전까지는 **배치를 갱신하지 않는다** — 모르는 것을 추측으로 계속 따라가면 결국 컨닝과 같아진다.

### 폐기한 설계 ②: 진짜 위치를 몰래 읽는 파견 (실패 기록) ★

2026-09-11 구현: 전역 몬스터만 제보 → 감독이 2.5초마다 **플레이어의 진짜 현재 위치** 주변 흐린 지점으로 가까운 2마리를 보냄. 매복 지점도 진짜 위치·속도로 계산.

문제 (2026-09-12 설계 검토):
1. 전역 몬스터가 놓친 뒤에도 6초간 진짜 위치를 읽었다 — 벽 뒤로 숨어 반대로 도망쳐도 따라온다. **따돌림이 성립하지 않는다.**
2. 구역 몬스터가 발견하면 포위가 없었다 — 한 마리와 1:1 술래잡기.
3. 놓치면 각자 자기 마지막 위치로 가서 한 점에 뭉쳤다.
4. "흐린 지점"도 결국 플레이어 주변 = 가까이 가기. 길을 막는 배치가 아니었다.

**교훈**: "흐리게 준다"는 정직성이 아니다. **정보의 출처**가 몬스터의 감각이어야 한다. 조정자에게서 Player 참조 자체를 없앴다.

### 폐기한 설계: 포위 대형 (실패 기록) ★

**이 절은 포트폴리오 서사로 남긴다.**

직전 구현은 "포위"였다. 0.25초마다 플레이어 현재 위치를 중심으로 반지름 10m 고리를 만들고,
몬스터를 자리에 배정해 3자리가 차면 일제히 덮치게 했다.
길목을 막으려고 첫 자리를 플레이어의 진행 방향에 두고, 플레이어를 관통하는 경로에는 가산점을 매겼다.

**플레이 테스트 결과: 전역 몬스터가 추적을 시작하면 4마리가 비엔나 소시지처럼 줄줄이 따라왔다.**

원인은 다섯 겹이었다.

1. 고리가 플레이어에 붙어서 같이 움직였다 — 플레이어가 달리면 고리도 달린다
2. 속도가 역전돼 있었다 — 플레이어 전력질주 11 > 몬스터 포위 이동 10. 앞자리에는 영원히 닿지 못한다
3. 뒤에서 쫓는 개체들이 같은 NavMesh 최단 경로를 받아 한 복도로 들어왔다
4. 포위가 완성돼도 전원이 플레이어 좌표로 직진 → 다시 한 줄
5. `Surround` 상태에 구역 제한이 없어 먼 개체까지 끌려와 줄 끝에 붙었다

**교훈**: 자리 배정 비용 계산·진행 방향 예측 같은 정교함은 **플레이어 눈에 보이지 않았고**, 보이는 결과는 행렬이었다.
"보이지 않는 곳에서 똑똑하고, 보이는 곳에서 멍청한" AI였다.
감독에게 정답을 쥐여주고 몬스터를 조종하는 대신, **정답을 흐려서 넘기고 발견은 개체에 맡기는** 쪽으로 바꿨다.

## 3. 개체 FSM (`MonsterAI`)

### 상태

| 상태 | 내용 |
|---|---|
| `Patrol` | 구역 내(또는 전역) 랜덤 지점 순찰 |
| `Investigate` | 소리·감독 호출을 받고 해당 지점으로. 도착 후 두리번거리다 순찰 |
| `Chase` | 시야 확보. 스타일별 추격 |
| `Return` | 자기 구역으로 복귀 |
| `Stun` | 레이저 피격. 굳음 → 자세 회복 |

`Surround` 상태는 포위 설계 폐기와 함께 삭제했다(2장 참조). 감독의 호출은 `Investigate`로 받는다.

### 함께 고친 버그 두 개

- **수색 중 새 지점을 받아도 무시됐다.** `ChangeState`가 같은 상태로의 전환을 무시하기 때문에,
  이미 `Investigate`인 개체는 소리를 새로 듣거나 호출을 다시 받아도 첫 지점에 머물렀다.
  → `RushToInvestigate()`로 목적지와 두리번 타이머를 직접 갱신
- **`investigateRushScale`이 먹지 않았다.** 소리를 듣는 순간 속도를 올려도 다음 프레임 `Update`가
  `investigateSpeed`로 덮어썼다. → 달려가는 중에는 `investigateSpeed × rushScale`을 유지하고, 다른 상태로 바뀌면 1로 돌린다

### 추격 스타일 수정

| 스타일 | 이전 | 지금 |
|---|---|---|
| `Pinky_Predict` | `velocity × 0.5` 고정 | `predictLeadTime`로 노출 |
| `Inky_Tactical` | `transform.right × 2` — **자기 기준** 2m 옆 | **플레이어 진행 방향 기준** 측면으로 `flankOffset`(4m) 파고듦 |

`Inky_Tactical`은 사실상 버그였다. 몬스터 자신의 오른쪽으로 2m 빗겨갈 뿐이라
직진 추격과 구별되지 않았다. 이제 플레이어의 이동 방향을 가로지르는 쪽으로 들어간다.

> 몬스터 4종의 성격 차별화는 **기획 결정 대기 중**이라 손대지 않았다.

하드코딩돼 있던 값을 전부 인스펙터로 꺼냈다.

| 항목 | 이전 | 지금 |

| 광폭화 지속·배율 | `3f` / `1.5f` (코드) | `berserkDuration` / `berserkSpeedScale` |

| 무리 호출 | 없음 → 포위 10개 필드(폐기) | 호출 6개 필드 (`dispatchInterval` / `dispatchBlurMin·Max` / `dispatchAngleJitter` / `callMemory` / `dispatchRange`) |

### 죽은 필드 제거
`contactDamage`(float, 10) — 선언만 되고 아무 데서도 쓰이지 않았다.
체력이 하트 5칸이므로 10이라는 값 자체가 의미가 없었다.

→ `contactDamageHearts`(int, 기본 1)로 교체하고 `PlayerHealth.TakeDamage(위치, 하트수)`에 실제로 전달한다.
**이제 인스펙터에서 만지면 실제로 달라진다.** 특정 몬스터만 2칸 깎게 하는 식의 차별화가 가능해졌다.
